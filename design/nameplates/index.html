      The proposed anchoring rules
      
    
      One model for every part of a plate. Today's code has seven separate placement paths (text, icons, indicator rows, two aura layouts, combo points, the soft-target icon, target arrows) and nine room values passed between them. This model replaces all of them. Everything here runs in the Designer: switch Rules to Current (v11) to see today's behavior on the same settings.
      

    
      1. An anchor is a point and a place
      
    
      Every part has an Anchor (the compass: Top Left, Top, Top Right, Left, Center, Right, Bottom Left, Bottom, Bottom Right) and a Place: Outside (around the health bar) or Inside (on it). Today, Left means "inside the bar" for text and "beside the bar" for icons. A Place setting makes the choice explicit, so an icon can sit inside the bar and text can sit beside it. Party Frames already use this model (place = "inside" | "outside").
      

    
      2. The plate's spine is fixed
      
    
      From the health bar outward, the order is fixed:
      
    
        
      
      1. The border line: aura rows set to Sit on Border and text placed On Border share one line right on the bar (your name top left, your debuffs top right). A name stops at the row's live edge.
        2. 
      
      2. The cast bar, Below or Above, 1px apart so the two boxes share one shadow pixel.
        3. 
      
      3. Cast texts placed outside the cast bar.
        4. 
      
      4. One text line for a name or health text placed Outside Top or Bottom.
        5. 
      
      5. An outside cast icon that spans both bars, which reserves its side.
        6. 
    
      
    
      All of these sizes are known in advance, so nothing in the spine moves on its own.
      

    
      3. Each anchor point holds an ordered stack
      
    
      Past the spine, every part anchored to the same point joins that point's stack, in an order you can change (Order in Stack: Closer to Bar, Farther). There are two kinds of member:
      
    
        
      
      • Badges are fixed-size parts: the raid marker, Elite and Rare, Quest, Level, combo points and target arrows. Badges at one point line up in one row, 2px apart. Each row starts at its point's edge:
        
          
          
        • Top Left: at the bar's left edge, running right.
          • 
          
        • Top Right: at the bar's right edge, running left.
          • 
          
        • Top: centered.
          • 
          
        • Left and Right: at the bar's side, running outward.
          • 
        
        
      
        • 
      
      • Aura rows are the aura groups. All groups on one point share one Blizzard aura container, so they can never overlap each other.
        • 
    
      
    
      Auras First (your baseline): on one anchor, the aura row sits closest to the bar and indicators come after it, anchored to the row's live end, so they slide in when the row is empty. Indicators First stays a choice. Target arrows are always last, anchored to the last part on their side.
      

    
      4. Grow away, chain by edges
      
    
      The rule that keeps secret auras from breaking the layout: an aura container sizes itself to the auras it shows. The game hides that size from ModeUI, but other frames can still be anchored to the container's edges, and the game resolves where they land. So a part placed past an aura row along its growth (target arrows set to Outside Everything) is anchored to the row's far edge. It moves as the row fills and empties, and ModeUI never measures anything. Rows grow away from the bar, so they never push a badge.
      
    
      Across its growth, a row's size is known: one line is one icon tall. So the soft-target icon clears the tallest Top stack using known heights, and stays still while auras come and go. (A row that wraps to more lines is counted at its full number of lines.)
      
    
      Frames anchored to a container must be created from Blizzard's DisableUntrustedLayoutScriptsTemplate. Otherwise they inherit a restriction that blocks their own layout scripts (see Research). An empty container is 1×1, so a part chained past it keeps a 1px gap plus spacing.
      

    
      5. Groups on one point: continue or stack
      
    
      Aura groups on the same point either Continue the Row, flowing one after another in one line (today's behavior), or each take a New Row (the container's forceNewLine, stacked across). Either way they are one container, ordered by layoutIndex, and a group with no auras adds no space. Per Row sets the container's maximum line size in pixels: Per Row × (icon width + spacing).
      

    
      6. Centered rows are really centered
      
    
      Today a Center row in the world puts its first icon in the middle and grows right, while the settings preview centers the whole row, so the two disagree. In the proposed model the container is anchored by its own center point and resizes itself, so it stays centered on whatever it shows. Lines that wrap stay left-aligned inside the centered block.
      

    
      7. Collisions are shown, not silently allowed
      
    
      Parts at different points (Top Left and Top, for example) don't push each other. The Designer outlines any overlap in red, counting each aura row at its full capacity, because that's how far it can reach in combat. The settings page preview would do the same.

      A Mode-wide rule this follows: icons are wider than tall, 4px shorter up to 35px wide and 6px from 36 (DESIGN_LANGUAGE.md, "Sizes"). Nameplate auras today are 6px shorter at every size; the Designer's Icon Shape Mode uses the shared rule.
      

    
      Pixel-perfect auras: the Cooldown Manager's model
      
    
        
      
      • Edge outside the icon. ModeCDM puts the frameThin edge outside each icon: a slot is the icon plus the edge's reach on every side, and Spacing counts between the shadows (ModeCDM/.../Layout.lua M.Geometry, M.IconReach). Nameplate auras today draw the rim inside the icon's size (Kit.LayoutAuraIcon), so a 22-wide icon shows a 20-wide picture and rows don't line up with CDM rows. The pass adopts the CDM model for nameplate auras through a shared helper, so both use one geometry. Party Frames and Buffs & Debuffs keep theirs.
        • 
      
      • Spacing −1. Neighbours share one shadow pixel (the Mode-Default rule), so the bands sit 1px apart.
        • 
      
      • Whole pixels. Every size and offset is snapped to physical pixels (Kit.PixelSize). Rows growing left or right are anchored by a corner, so they always land on whole pixels.
        • 
      
      • Centered rows are anchored by their own center, and their length is secret. A row of n icons is n × (slot + spacing) − spacing wide. When slot + spacing is even, that length is always odd (or always even), so one fixed half-pixel nudge puts every count on whole pixels. When it's odd, some counts land between pixels. The Designer checks this and suggests a width; 33 for crowd control passes.
        • 
      
      • The container's own spacing takes the slot size (elementWidth/elementHeight = slot) and the spacing, so the game's layout and the CDM geometry agree.
        • 
    
      

    
      Finding 1: why the preview jumps and drifts off center
      
    
      In Modules/Nameplates/Preview.lua there are three causes:
      
    
        
      
      1. A third copy of the layout. PreviewBounds (lines 152-193) re-estimates how far the plate reaches instead of asking the layout. Its estimates are rough:
        
          
          
        • it adds the arrows on both sides whether or not they show;
          • 
          
        • side aura rows count as icon count × width plus the absolute offset;
          • 
          
        • Top and Bottom take only the tallest item.
          • 
        
        
        When the estimate is wrong, the plate is placed off center.
        2. 
      
      2. Measured one step late. RenderPreview (lines 211-216) lays the plate out, measures it, and only then paints the sample. Painting sets the indicators, which changes the room beside the bar and moves the aura rows. So each anchor change is centered with the previous change's numbers.
        3. 
      
      3. It centers the whole footprint on purpose. Moving buffs from the right to the left slides the health bar sideways. GetPreviewSize also changes the preview's height, so the page below jumps.
        4. 
    
      
    
      Fix: the stack engine returns every part's exact box. The preview measures after painting, from that one source. The health bar stays pinned in the middle, the preview zooms out if the footprint doesn't fit, and its height stays fixed for each kind.

      Finding 2: parts inside the bar drawn behind it
      
    
      Frame levels today, in Plate.lua and Layout.lua. For each box at level B:
      
    
        
      
      • the bar is B+1;
        • 
      
      • the Comet spark's clip frame is B+2;
        • 
      
      • the rim holder is B+3.
        • 
    
      
    
      The text layer, which holds inside text, the raid marker, the level and the elite icon, is set to the health box + 3: the same level as the health rim. The cast box is a sibling at the same B, so its rim also sits at the text layer's level, which is where the cast texts live. Two frames at the same strata and level have no guaranteed order, so which one draws on top can change. In the world it is worse: the text layer's level is set once per layout, while the game reorders plates as they overlap.
      
    
      Fix:
      
        
        
      • Order by parent, not by number. The inside layer becomes a child of the health box's rim holder, and the cast texts a child of the cast rim holder. A child frame always draws above its parent.
        • 
        
      • Outside parts and auras go on their own layers with clear gaps.
        • 
        
      • Levels are set again whenever a plate gets a unit.
        • 
        
      • A test checks the order.
        • 
      
      
      If you see it again before then, /fstack over the hidden part would confirm it.
      

    
      Finding 3: the "combat" and "loot" icons
      
    
        
      
      • The sword, bag and gear over plates are soft-target icons, from the game's Accessibility interact-icon setting. Blizzard draws them in its own plate's SoftTargetFrame, which fades with Blizzard's art on a ModeUI plate. ModeUI then draws the same cursor art itself (SoftTarget.lua, SetUnitCursorTexture). So the sword you see on a ModeUI plate is ModeUI's own icon.
        • 
      
      • Plates ModeUI leaves to Blizzard (widget-only plates, your personal resource display, friendly plates inside instances) still get Blizzard's icon. Objects such as chests, herbs and mailboxes get icons the game draws in the world itself, with no frame; the CVar SoftTargetIconGameObject controls those.
        • 
      
      • Unit frames: Blizzard's Player combat icon (AttackIcon, UI-HUD-UnitFrame-Player-CombatIcon), rest icon and corner icon are all inside PlayerFrameContent, which Unit Frames already fades. In Forever's unit frame code, nothing that would show a combat or loot icon ignores its parent's fade. The only nameplate part that does is selectionHighlight, a faint tint on the target's bar, not an icon.
        • 
    
      
    
      Plan:
      
        
        
      1. ModeUI's soft-target icon gets a choice, Loot and Interact (default), All or None, so the sword never shows.
        2. 
        
      2. An opt-in Hide Blizzard's Combat Icon sets SoftTargetIconEnemy (and SoftTargetIconFriend) to 0, remembers the old values and puts them back when turned off. It changes a game setting, so it is off until you turn it on. Loot icons stay.
        3. 
        
      3. If an icon still shows on a unit frame, hover it with /fstack and send a screenshot; its frame name tells me what to add to the fade list.
        4. 
      
      
    
      

    
      Finding 4: what can't be exact
      
    
        
      
      • The name's length is a width set by the debuff row's edge, not a character count, because a secret name can't be cut in Lua.

      Research
      
    
      Sources: Blizzard's interface code on the forever branch of Gethe/wow-ui-source (commit 734f065, "1.60.1 (71037)", November 20, 2026), compared with live (12.1.5); the source of Platynator (v550, interface 16001), Plater, ElvUI with oUF, ThreatPlates, BetterBlizzPlates (which has a forever folder) and Kui; and warcraft.wiki.gg. Nothing here has been tested in game.
      

    
      
      
      Aura containers size themselves. After each layout the container calls SetSize(secretwrap(w, h)) (Blizzard_CustomAuraContainer.lua:799-801). ModeUI can't read the size, but it can anchor frames to the container's edges. ThreatPlates and BetterBlizzPlates already chain buffs to the debuff container this way on 12.x.
      
      
      Anchored frames need a template. Adding a group gives the container the forbidden aspect UntrustedLayoutScriptExecution, which spreads to anything anchored to it and blocks OnSizeChanged. Blizzard's own comment says such frames should be created with DisableUntrustedLayoutScriptsTemplate (ForbiddenAspectTemplates.xml:18-22).
      
      
      ModeUI's Center growth is wrong in the world. AuraContainers.lua anchors a corner, centers the first icon and grows right. Anchoring the container by a single CENTER point centers the whole row; Platynator and oUF both do this.

      Click area and plate size. The game sizes the plate with C_NamePlate.SetNamePlateSize (restricted). C_NamePlateManager.SetNamePlateHitTestInsets is restricted and refuses secrets. The plate's own SetAllHitTestPoints works for addon code only on the tick a unit is assigned, while in combat. SetStackingBoundsFrame is documented. Platynator uses these behind existence checks to fit clicks and stacking to its own art. ModeUI leaves them to Blizzard, so a ModeUI plate narrower than 166 sits inside a wider click area. Keeping that is the safe default; fitting it is a later, separate pass. C_NamePlate.GetNamePlateSize() reads the size safely.
      
    
      Legacy CVars. nameplateWidth, nameplateOverlapH/V, nameplateLargerScale, nameplateHorizontalScale and nameplateMotion appear nowhere in Forever's interface code. Each needs a C_CVar.GetCVar check in game before any setting relies on it.
      

    
      The aura container (exists on Forever, identical to live)
      
    
        
      
      • Layout, for the whole container: SetFlowLayoutAxis, SetFlowLayoutAnchorPoint, SetFlowLayoutGrowthDirection(h, v), SetFlowLayoutPadding, SetFlowLayoutMaximumLineSize(px). Lines wrap at a size in pixels; there is no count per row.
        • 
      
      • Per group (SetAuraGroupLayout): elementSpacing, lineSpacing, groupSpacing, groupLineSpacing, forceNewLine, elementWidth/elementHeight (they reserve space only; they don't resize the button), layoutIndex.
        • 
      
      • Order: groups are sorted by layoutIndex, then by the order they were added, and laid out in one flow. Empty groups add no spacing and force no new line, decided in secure code (AnchorUtil.lua:615, 693).
        • 
      
      • Sorting: Default, BigDefensive, UnitFrameDebuff, ImportantOnly, Expiration, Name and more.
        • 
      
      • Candidate filters: isStealable, nameplateShowPersonal, nameplateShowAll, isBossAura, includeSpellIDs, maxDuration and more. Blizzard's enemy debuffs require yours plus nameplateShowPersonal.
        • 
      
      • Buttons get DenyTaintedAccessWhenAurasAreSecret after login. ModeUI already styles them in initializeFrame, which is right. The button methods include SetSpellName, SetCasterName and SetDurationBar.
        • 
      
      • Creating containers in combat: ElvUI, ThreatPlates and Plater each keep a pool of about 40, suggesting creation is blocked or unsafe in combat. ModeUI creates a plate's containers when the plate first gets a unit, which can happen in combat. This needs a check in game.

      UnitHealth, GetRaidTargetIndex, UnitSpellTargetName/Class, UnitCastingDurationAlwaysPass to SetValue, SetSpriteSheetCell, SetText
      
        
      UnitNameUnder unit-identity rules (not player-controlled or in your group)SetText. Its width may not be measurable: GetStringWidth is flagged only SecretWhenAnchoringSecret. Test it.
      
        
      UnitCastingInfo/UnitChannelInfoUnless you or your pet; castBarID is never secretAs today
      
        
      Aura dataCombat, encounters, Mythic+, PvPOnly through containers
      
        
      UnitClassification, UnitLevel, UnitReactionNo secret flagsBadges can be sized from them
      
        
      Container and anything anchored to itAlways (GetWidth, GetRect)Anchor to it; never read it
      
            
    
      
    
      From tainted code, SetShown, SetPoint, SetSize and SetScale refuse secrets, so only Blizzard's secure layout can place anything by a secret. SetAlphaFromBoolean and SetVertexColorFromBoolean accept them. Plater and Platynator show the not-interruptible shield with SetAlphaFromBoolean(notInterruptible). ModeUI avoided it because its alpha range is undocumented; their use is precedent, but it still needs a check in game.
      

    
      Cast bar facts
      
    
        
      
      • UNIT_SPELLCAST_INTERRUPTED and CHANNEL_STOP carry an interruptedBy GUID. Blizzard writes "Interrupted by [name]" through UnitNameFromGUID (CastingBarFrame.lua:618-635), and Plater and Platynator show the interrupter's name class-colored.
        • 
      
      • UnitSpellTargetName/Class give the spell's own target. ModeUI's Cast Target uses UnitName(unit .. "target"), the caster's current target, which differs for spells cast at someone else.
        • 
      
      • Blizzard highlights important casts (C_Spell.IsSpellImportant; ImportantCastIndicator). Whether its answer is secret is not documented.
        • 
      
      • Every addon draws a shield on the cast bar's left edge for casts you can't interrupt; Blizzard puts it in the icon's place.
        • 
    
      

    
      Native collapse
      
    
      Blizzard chains raid mark → elite icon → buffs with the XML attribute collapsesLayout="true": when one is hidden, the next takes its place inside the engine. The Lua setter is protected. Whether an addon's own XML can use the attribute, and whether it collapses on a secret Shown state, is unverified. If it works, badge rows could close gaps without Lua.

      • Platynator: drag on a big preview, the anchor point picked by quadrant, 1px arrow-key nudges, preview auras drawn at the configured limit so users see how far a row can reach.

        • 
      
      • ElvUI and ThreatPlates: an "attach to" choice with loop detection.

      Problems found
      
    
        
      
      1. Top and Bottom overlap. The raid marker, an indicator row, an aura row and combo points anchored to any Top point all start at gap + plate.above. Only side anchors chain.
        2. 
      
      2. The preview and the world disagree on Center growth (reader vs container).
        3. 
      
      3. Combat pushes arrows and side combo points far out. They clear a side row's full capacity because the container can't be measured (AuraContainers.lua:186-189).
        4. 
      
      4. Containers may be created in combat. AttachAuraContainers runs when a plate first gets a unit; other addons pool containers instead. Needs a check.
        5. 
      
      5. Cast Target is the caster's target, not the spell's target.
        6. 
      
      6. Anchors mean different things for text and icons (Left is inside for one and beside for the other).
        7. 
      
      7. Settings use flat keys per part (questAnchor, questX…). Party Frames use one table per part, so the two modules differ.
        8. 
      
      8. Settings.lua is at 378 of 400 lines, so new controls need a split first.
        9.
